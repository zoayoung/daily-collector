# 规格：采集口径对齐与新爆款优先

**Status:** ready-for-agent
**日期:** 2026-10-31
**影响阶段:** 采集（候选集、入榜集、分层排序）、契约、校验、整理排序、渲染、文档与测试

## Problem Statement

日报的“趋势”仍然由资历决定，而不是由“今天刚冒头”决定。

- 采集排序只看数据归属日新增 star：一个十万 star 的老项目当天多涨几十个，就会压过刚发布三天、当天涨几百的新项目。
- 候选集缺少“近 7 天创建”的切片。现有新仓库通道是“近 30 天创建 + ≥50 star”，刚冒头两三天的项目既可能 star 还不够高，也可能被更老的“新仓库”挤掉。
- 候选集没有任何相关性预筛，Awesome 列表、纯罗列类仓库、连 description 都没有的空壳都占用候选位与增量预算。
- 采集产物不保留 GitHub `topics`，分析阶段打自由标签时缺少最便宜的一手素材。
- 读者看到的是：同一批老牌项目反复出现，新爆款要等它涨到很大才可能被看见。

对照目标形态（一个「GitHub 热门项目」采集技能：近 7 天创建、按 star 取前 30、按相关性过滤、按 `full_name` 去重、输出中文摘要、取 Top 15），当前系统在“新近度”“相关性过滤”“topics 字段”三处偏离；但在“数据归属日增量”“30 天重复窗口”“脚本化可复现”三处明显更强，不能整段照搬。

## Solution

保留采集脚本作为执行者，只吸收目标形态中真正缺失的口径，并新增“新爆款优先”的分层排序：

- 新增第三条候选通道「近 7 天新建」：数据归属日前 7 天创建、累计 star ≥100。
- 候选集增加可判定排除：Awesome 列表、无 description 的仓库硬剔除；无 README 只对准备入榜的候选检查，且设预算上限；刷星不做自动判定，只在 `gaps` 说明。
- 采集产物保留 `topics`，供分析阶段打自由标签。
- 新爆款定义为「数据归属日前 7 天创建且累计 star ≥100」，由 `created_at` 与 `stars_total` 推导，不新增布尔字段。
- 入榜集、定稿集、渲染统一采用分层排序：新爆款恒在前，组内按数据归属日新增 star 降序；老项目排在其后。
- 日报标题为入榜名次加 `🆕` 标记；概览不单列“新爆款”组；质量评分不因新近度加分。

读者看到的是：新爆款先出现、带 `🆕` 标记，老项目只在没有新爆款时占据前列。

## User Stories

1. 作为日报读者，我希望新爆款（近 7 天创建且 ≥100 star）排在所有老项目之前，以便一眼看到今天刚冒头的东西。
2. 作为日报读者，我希望每个新爆款的标题带 `🆕` 标记，以便不必回看创建日期就能分辨。
3. 作为日报读者，我希望新爆款组内仍按数据归属日新增 star 降序，以便组内轻重可比较。
4. 作为日报读者，我希望老项目组内仍按数据归属日新增 star 降序，以便榜单口径不变。
5. 作为日报读者，我希望近 7 天新建的项目能被单独搜索到，以便 star 还不够高但当天暴涨的项目不被 30 天通道挤掉。
6. 作为日报读者，我希望 Awesome 列表不再出现在日报里，以便每天看到的是项目而不是索引。
7. 作为日报读者，我希望没有描述的空壳仓库被剔除，以便每条都有话可说。
8. 作为日报读者，我希望没有 README 的项目在入榜前被剔除，以便点进去能看到资料。
9. 作为日报读者，我希望新爆款不足时老项目自然补位，以便不出现为凑数硬塞的条目。
10. 作为日报读者，我希望当天所有增量都为 0 时仍先展示新爆款，以便兜底排序不推翻分层规则。
11. 作为日报读者，我希望重复窗口（30 天，不含发布日）继续生效，以便新爆款优先不会变成同一批项目刷屏。
12. 作为日报读者，我希望 30 天外再次出现的项目仍带 `🔁 重复：上次 YYYY-MM-DD`，以便重复标记不被本次改动破坏。
13. 作为日报读者，我希望概览仍按自由标签合并为不超过 6 组，以便不因新增“新爆款”维度破坏阅读结构。
14. 作为日报读者，我希望评分只反映文字质量，以便“新但写得差”的条目仍会被打回。
15. 作为日报读者，我希望 star、增量、创建日期等数字照抄采集结果，以便数据可信。
16. 作为分析者，我希望采集结果带上 `topics`，以便打自由标签时有一手素材，减少抓 README 的次数。
17. 作为分析者，我希望 `topics` 缺失时仍能正常打标签，以便旧采集产物无需迁移。
18. 作为分析者，我希望分析阶段不改变分层顺序，以便整理阶段继承同一口径。
19. 作为整理者，我希望定稿排序沿用“新爆款在前、组内按增量降序”，以便渲染只做排版。
20. 作为整理者，我希望批量剔除时仍能记录理由与计数，以便事后追查。
21. 作为维护者，我希望采集统计能分别看到三个通道的候选数，以便判断“近 7 天新建”通道是否真的有效。
22. 作为维护者，我希望三个通道计数之和等于候选总数，以便统计自洽可校验。
23. 作为维护者，我希望被排除规则剔除的数量独立统计，以便把它与重复窗口剔除区分开。
24. 作为维护者，我希望 README 检查有预算上限，以便扩容不会把核心配额吃光。
25. 作为维护者，我希望 README 接口返回 404 视为“无 README”剔除，其他错误保留并记入 `gaps`，以便网络抖动不会误杀项目。
26. 作为维护者，我希望刷星不做自动判定，以便不引入不可解释的黑名单。
27. 作为维护者，我希望新爆款判定由 `created_at` 与 `stars_total` 推导，以便产物里没有可能过期的冗余布尔值。
28. 作为维护者，我希望校验脚本按同一分层口径硬校验，以便整理阶段不能把老项目排到新爆款前面。
29. 作为维护者，我希望边界日期（数据归属日与发布日相差一天时）不被校验误杀，以便本地与 CI 的日期口径都能通过。
30. 作为维护者，我希望旧的两键通道统计产物继续通过校验，以便历史产物与本地差分基线不被破坏。
31. 作为维护者，我希望旧的无 `topics`、无新统计字段的产物继续通过校验，以便 `--all` 回归不受影响。
32. 作为维护者，我希望候选集扩容后搜索配额仍在限频内，以便定时任务不因 429 失败。
33. 作为维护者，我希望采集、校验仍由脚本完成，以便成本与口径可复现（沿用采集由脚本承担的决策）。
34. 作为维护者，我希望不新增可加载技能，以便“子代理只有两个”“主代理不能加载流程技能”的约束不被打破。
35. 作为维护者，我希望采集口径只有一处来源，以便 AGENTS.md 只留指针、细则在 spec。
36. 作为维护者，我希望把这次决策写成规格并可拆成工单，以便按契约先行的顺序实施。
37. 作为维护者，我希望测试仍只走既有 CLI 接缝，以便不为内部函数新增测试接缝。
38. 作为维护者，我希望回放服务器能区分第三条通道并返回 README 404，以便测试覆盖新行为而不打真实网络。
39. 作为维护者，我希望渲染的 `🆕` 标记能被机械验证，以便不靠人眼检查排版。
40. 作为维护者，我希望失败场景（README 检查预算耗尽）在 `gaps` 里可见，以便知道为什么入榜不足。

## Implementation Decisions

**执行形态**

- 采集仍由采集脚本承担，不新增可加载技能，不恢复 WebFetch 交互采集（尊重“采集由脚本承担”的架构决策）。
- “采集技能”在本规格中仅指口径参照，不产生新的执行载体。

**候选集**

- 三通道并列：star 区间通道（现状不变）、新仓库通道（现状不变）、新增「近 7 天新建」通道。
- 近 7 天新建通道：`created >= 数据归属日 - 7 天`、`stars >= 100`、`sort=stars`、`order=desc`、`per_page=100`、最多 2 页；第一页不足 100 条不再翻页。
- 合并顺序与通道归属：star 区间通道先收集，其次新仓库通道，最后近 7 天新建通道；按 `full_name` 大小写不敏感去重，保留首次出现的原始大小写与通道归属。
- 通道归属只用于统计，不决定分层；分层只由 `created_at` 与 `stars_total` 推导。

**字段**

- 仓库条目新增可选 `topics`：字符串数组，元素非空且不重复；采集缺失时写空数组，旧产物可省略该字段。
- 采集与分析产物都把 `topics` 原样透传；分析阶段是否使用它不影响契约。

**排除规则（候选集阶段）**

- 硬剔除 Awesome 列表：仓库名（`full_name` 的 repo 段）包含 `awesome`（不区分大小写），或 description 以 `a curated list` / `curated list` 开头（不区分大小写）。
- 硬剔除无 description：缺失、`null` 或去空白后为空。
- 实施顺序：搜索去重 → 统计通道 → 应用排除 → 30 天重复窗口过滤 → 得到 `eligible`。
- 统计口径：`eligible = candidates - excluded - dropped_recent_duplicates`；`excluded` 为新增可选统计字段，旧产物缺失按 0 处理。

**README 检查（入榜阶段）**

- 在增量计算与分层排序之后、取前 50 条之前，按排序顺序逐个检查 README。
- 预算上限 100 次/轮；检查到已凑满 50 条或预算耗尽即停。
- `GET /repos/{owner}/{repo}/readme`：404 视为无 README 并剔除；其他错误保留该条并写入 `gaps`。
- 剔除数写入新增可选统计字段 `readme_dropped`；预算耗尽时 `gaps` 说明“另有 N 条未做 README 检查”。
- `eligible` 仍在 README 检查之前计算，二者互不重算；`eligible < 入榜条数` 的既有校验收敛为“`eligible` 不小于通过 README 检查后的入榜条数”。

**分层排序**

- 新爆款 = `created_at >= 数据归属日 - 7 天` 且 `stars_total >= 100`，由现有字段推导，不新增 `is_new`。
- 排序：先按“是否新爆款”分层（新爆款优先），层内按 `stars_today` 降序。
- 全零退化：当所有 `stars_today` 为 0 时，层内改为按 `stars_total` 降序；分层规则不变。
- 采集入榜集、分析产物顺序、整理 `rank`、渲染顺序使用同一规则。
- 校验脚本把“`stars_today` 单调降序”替换为“分层内单调降序且老项目不得出现在新爆款之前”。
- 边界容错：产物只携带发布日，而分层基准是数据归属日；校验按发布日推算时，对 `created_at` 恰为「发布日 - 8 天」的条目接受任一分层，其余严格校验。这样本地（基准=发布日）与 CI（基准=发布日前一天）都能通过。

**契约**

- 公共仓库条目片段新增可选 `topics`。
- 采集统计新增可选 `excluded` 与 `readme_dropped`（非负整数）。
- 通道统计扩展为三个键：`star_bands`、`new_repos`、`new_7d`；新产物必须写全三键且三键之和等于 `candidates`；旧的两键产物仍有效，校验只要求“存在键之和等于 `candidates`”。
- 仓库条目不新增 `is_new`、`source`、`channel` 等字段。

**渲染**

- 新爆款标题为 `### {rank}. 🆕 {full_name}`；其余标题格式不变。
- 概览不新增“新爆款”分组，仍按自由标签合并为不超过 6 组。
- 质量评分维度与阈值不变，不因新近度加分。

**文档**

- 工作流 spec 同步：候选池（三通道）、排除规则、统计口径、分层排序、渲染模板与 `🆕` 标记。
- `GLOSSARY.md` 新增「新爆款」词条，并澄清「采集」与“采集技能”不是同一概念。
- `AGENTS.md` 只更新入口级指针，不复制细则。
- 不新增技能；整理技能只改排序口径描述。

## Testing Decisions

- 好测试的标准：只断言外部可观察行为——命令退出码、stderr、写出的 JSON 内容与跨文件一致性；不 import 内部函数，不锁定函数名或局部变量。
- 接缝：沿用现有最高接缝「CLI + 产物文件」。本次只用两条：采集 CLI 与校验 CLI；打分 CLI 不涉及。不新增模块级接缝。
- 回放支撑：沿用 `FixtureServer` 回放 GitHub 响应与 `run_cli` 执行脚本的现有做法，扩展到按通道（含 `new_7d`）返回不同 fixture，并能对新端点（README）返回 404 或 200。
- 先例：`tests/test_new_repo_channel.py`（多通道查询、翻页、去重、旧产物兼容）、`tests/test_duplicate_window.py`（窗口过滤与硬校验）、`tests/test_candidate_pool.py`（查询条件）、`tests/test_validation_thresholds.py`（跨文件统计自洽）。
- 需要覆盖：第三通道的查询条件与翻页；三路去重与通道归属；三键计数之和等于 `candidates`；排除规则（Awesome、无 description）；README 404 剔除与预算耗尽；分层排序（采集、分析顺序、整理 `rank`）；边界日期容错；`topics` 透传；新增统计字段缺失时的旧产物兼容；整理阶段“老项目不得早于新爆款”的硬校验负例。
- 渲染不在脚本接缝内：主代理渲染属人工验收，端到端检查 `### {rank}. 🆕 owner/repo` 是否存在、非新爆款是否无标记。
- 不新增网络依赖：所有新端点均走回放服务器；真实 API 只用于人工端到端一次。

## Out of Scope

- 把采集改为 agent + WebFetch 交互采集，或新增可加载“采集技能”。
- 改输出目录与文件名（从 `work/` 的采集产物迁到 `knowledge/raw/`）。
- 用累计 star 排序替代数据归属日新增 star。
- 在采集阶段写中文摘要（摘要仍由分析、整理阶段产出）。
- 未认证调用 GitHub API。
- 质量评分加入新近度维度，或概览单列“新爆款”组。
- 自动判定刷星 / star 异常增长。
- 修改 30 天重复窗口、`pushed` 过滤、增量兜底预算（150 次/轮）、入榜 50 条上限、定稿 10–15 条规则。
- 修改 CI 排班、幂等、回写与凭证配置。

## Further Notes

- 配额估算：搜索请求由约 10 次升至约 12 次/轮（限频 30 次/分）；README 检查新增最多 100 次核心请求；增量兜底仍 ≤150 次/轮（核心限频 5000 次/时）。
- 日期口径：近 7 天通道与“新爆款”判定均以数据归属日为基准；30 天新仓库通道维持发布日基准，两者并存，文档需写明差异。
- 分层排序的边界容错只影响校验，不改变采集脚本的真实分层；目的是让产物不必携带数据归属日也能被校验。
- 本次决策与既有架构决策一致：采集仍由脚本承担、标签仍自由、评分仍只衡量文字、30 天窗口仍零例外。
- 术语：新增「新爆款」；「分层排序」可作为实现词但不进词汇表；“采集技能”不进入词汇表，避免与「采集」混淆。
