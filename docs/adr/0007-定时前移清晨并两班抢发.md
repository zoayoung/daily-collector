# 定时前移到清晨 06:00，并用两班抢发

2026-10-24 的定时 run 由 GitHub 在 04:07 UTC（12:07 UTC+8）才创建：cron 写的确实是 `0 0 * * *`，但事件在 GitHub 调度层就排队了约 4 小时；再往前一天（10-23）那次定时则整条没有出现。也就是说，`schedule` 只是「到点尝试」：整点属于高负载时段，可能被推迟数小时，也可能被丢弃。准点发布无法在 GitHub Actions 上被锚定。

因此目标改为「清晨 06:00（UTC+8）开始、08:00 前完成」：两班非整点 cron（`22:07` 与 `22:47` UTC，即 06:07 / 06:47 UTC+8），靠已有的幂等检查先到先发、后到跳过；`daily` 的 `timeout-minutes` 收到 45，使最后一班即便按时启动也能在窗口内收口；两班都被推迟时照常发布，只在运行摘要里标注「超窗」。数据归属口径不变：仍是发布日的前一个自然日，与触发时刻无关。

## Considered Options

- 单班 `0 0 * * *`（ADR-0006 现状）：08:00 整点、负载最重，实测可晚 4 小时甚至整条丢弃。
- 单班错峰 `22:07` UTC：避开整点尖峰，但没有任何冗余，丢班即当天无日报。
- 两班非整点 `22:07` / `22:47` UTC：任一班正常触发都能在 08:00 前完成，另一班被幂等跳过。
- 外部定时器调 `workflow_dispatch`：能绕开 `schedule` 的排队，但要多一个密钥与外部服务，且落在「除 GitHub Actions 之外的调度方式」的范围外。

## Consequences

- 发布窗口为 06:00–08:00（UTC+8）；正常一跑 7–9 分钟，窗口对单班足够宽。
- 仍然可能超窗：GitHub 的定时延迟不可控，本决策只降低概率，不提供保证。
- 本地差分的取数时刻从 08:00 前移到约 06:00，与日历日归属窗口错开约 6 小时；该窗口只在拿不到 star 历史时作近似，口径不变。
- 迟到不丢日报：超窗运行照常发布，事后可在运行摘要看到标注。
- ADR-0006 的定时选择由本文件取代，其数据归属口径与其余决策继续有效。
