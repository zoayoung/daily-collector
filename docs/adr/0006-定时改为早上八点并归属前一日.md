# 定时改为 08:00 UTC+8，数据归属前一日

> 定时时间后来前移到清晨 06:00 并改为两班抢发，见 ADR-0007；数据归属口径与其余决策仍有效。

日报的原始需求是每天早上 8 点（UTC+8）自动采集，但 ADR-0004 为了拿到当日 star 增量把 cron 改到了 22:00 UTC+8。实际运行中，定时还会被 GitHub 推迟并跨过午夜：2026-10-22 的 22:00 触发延迟到次日 02:27 才执行，写出的却是次日日期的日报。现在改回 `0 0 * * *` UTC（08:00 UTC+8）：发布日仍是运行日，数据归属改为前一个完整自然日（D-1）。文件名继续按发布日 D 命名；数据归属日与发布日不同时，日报与 token 报告内部标注「统计窗口：昨日到今日（UTC+8）」。这样浏览 `daily-knowledge/` 时每天都有当天文件，时间口径在正文里说明。

采集时 `--date D --gain-date D-1`：发布日 D 用于 30 天去重窗口、候选搜索的推送时间窗、本地差分基线与幂等检查；数据归属日 D-1 只用于 `stargazers/history`。`stargazers/history` 给出 D-1 这个日历日的完整增量；本地差分以上一发布日的 `collect.json` 为基线，窗口是上次 08:00 到本次 08:00，与日历日窗口错开 8 小时，仅在拿不到 star 历史时作近似，避免新项目被 0 压低、榜单退化成总 star 榜。

## Considered Options

- 08:00 UTC+8 + 当天口径：数据不完整；无基线的候选拿到 0，排序偏向有昨日基线的旧候选。
- 22:00 UTC+8 + 当天口径：数据完整，但不符合「早上八点」的需求，且延迟跨午夜会写错日期。
- 08:00 UTC+8 + 前一日口径，文件名也用 D-1：数据完整，但文件名与阅读日错位；以文件名为日期做去重时还会漏掉最近一份日报。
- 08:00 UTC+8 + 前一日口径，文件名用 D、内部标注 D-1：数据完整，文件名与阅读日对齐，时间口径在正文可见。

## Consequences

- 定时任务的发布日为运行日，数据归属为前一天；手动 `workflow_dispatch` 与本地触发两者都取当天。手动触发也注入 `KNOWLEDGE_DATE`/`KNOWLEDGE_GAIN_DATE`，只是两者同值。
- 发布日通过 `KNOWLEDGE_DATE`、数据归属日通过 `KNOWLEDGE_GAIN_DATE` 贯穿工作流、`collect.py` 与 token 插件；日报和 token 报告都按发布日命名，数据归属日不同时在正文标注「统计窗口：昨日到今日（UTC+8）」。
- 30 天去重窗口、候选搜索的推送时间窗、本地差分基线、幂等检查与 artifact 路径都以发布日为准；只有 `stargazers/history` 查数据归属日。
- GitHub Actions 的定时是尽力而为，实际触发可能晚于 08:00；`0 0 * * *` 距 UTC+8 日界有 16 小时，常规延迟仍产出数据完整的前一日日报。
- 2026-10-23 日报在旧口径下已提前发布；切换后 10-24 08:00 会发布 10-24（数据归属 10-23），与旧 10-23 日报存在一次内容重叠，之后每天一份。
- ADR-0004 的定时选择由本文件取代，其余流水线决策继续有效。
