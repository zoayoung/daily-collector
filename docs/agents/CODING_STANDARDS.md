# 编码规范

本仓的判断类规范，供 `/code-review` 的「标准轴」审查时阅读。这里只放**判断类**规范——无法用工具机械判定、只能靠审查判断的跨文件一致性；机械类（格式、语法）交给工具，不在此列。

## 单一来源

每份口径只写一处，改行为只改一处。

- **字段与形状**——JSON 的字段名、类型、必填项、枚举——以 `schemas/` 为唯一来源。
- **产品口径**——业务语义、取值规则、数值常量、域名与查询串——以 `.scratch/knowledge-daily/spec.md` 为唯一来源。
- `.agents/skills/` 与 `.opencode/agent/` 承载流程与指针：需要产品口径时写「见 spec『X』节」，不复述其内容。
- 评分词表与阈值归 `config/score-rules.json` 与 spec，不在脚本或技能里另写一份。

判据（审查用）：若某个数字 / 枚举 / 域名 / 字段清单同时出现在 spec 与某技能或 agent 中，即报 `[判断]` 违反；若字段名同时手写在 schema 与校验脚本里，同样视为重复（脚本应读 schema 或集中定义）。

机械线索（可选，手动跑）：下面这条命令列出技能/agent 里疑似复述 spec 口径的行。它是**线索清单，不是门禁**——命中行逐条对照 spec 判断：只有 spec 已定义的口径（数值/枚举/字段清单）才算复述，操作必需者不算。

```sh
git grep -n -E '≤ ?[0-9]|15[–-]20|[0-9]+ ?(个?汉字|次/|天|词|条)|字段齐全' -- .agents/skills .opencode/agent
```

## 脚本

- 中文注释、中文错误信息；stdout 面向人（成功/失败摘要），`--json` 面向程序（插件、hook），两者不混。
- 只做本阶段的事：采集不判主题，校验不评文笔，评分不改文件内容。
- 失败即非零退出并写清原因；不写半成品正式产物（诊断用文件需以 `.partial.json` 命名）。
- 路径从仓库根解析（脚本按自身位置定位根目录），不依赖调用时的 cwd。
- 依赖只走 `uv`（`pyproject.toml`）；不引入第二套环境或全局安装步骤。

## 插件

- 插件是薄壳：只做「监听 → 调脚本 → 展示结果」，判定口径一律留在 Python 脚本里。
- 不阻断主流程：脚本失败时追加警告，不抛错打断子代理。
- 不改写工具结果的语义（只追加只读信息），不修改用户或其他阶段的文件。
- 只监听约定的事件/工具与路径，其余零副作用。

## 为什么

口径复述会漂移：改一处漏改另一处，规范与产出互相矛盾。本仓曾因此同时出现多组 spec 与技能不一致的缺陷。
